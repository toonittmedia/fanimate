# Fanimate Phase 1: Foundation

Companion to the [product vision](../product-vision.md). The brand assets proposed in section 1 live in [`brand/`](../../brand/). Phase 1 was first planned at about 12 months. M0 to M5 were built in about a week, so the rest is set by user testing rather than by coding (see [section 4.1](#41-schedule)). **Phase 1 no longer ends at a public release.** On 2026-10-30 the owner moved **Gate 1: version 1.0** (with the public beta and the launch) to the end of [Phase 2](phase-2.md), so that films, examples and handmade templates exist before the public sees Fanimate; the reasons and the plan are in [release-1.0.md](release-1.0.md). Phase 1 ends at a close-out (the exit checks of M2 to M5 with testers, no known data-loss bugs, the other platforms' benchmarks), while the closed alpha continues. Section 5 below still defines the Gate 1 tests; they are evaluated at the end of Phase 2. This document starts with the brand, because every screen, installer and website in Phase 1 depends on it, and then breaks the engineering work into workstreams, milestones and acceptance tests.

> **What comes from the vision and what is new.** The scope, the Gate 1 criteria and the performance budget are taken from the product vision. The brand proposals, the milestone order, the task lists and the acceptance tests are new proposals, written so the team can challenge and change them.

- [x] GPU benchmark without a window (`fanimate-cli bench --gpu`): evaluates, tessellates and renders offscreen with 4× MSAA, waiting for the GPU every frame. Every release build runs it, with a headless render, on Windows, macOS and Linux and records the output in the run summary
- [x] Headless determinism (the WS1 "done when"): a scene built and animated in code, saved and reopened with no UI, evaluates identically on every frame and saves to the same bytes; the same frame renders to the same pixels
- [x] Reference hardware proposed ([reference-hardware.md](../reference-hardware.md)), waiting for the maintainers to confirm
- [x] Import test corpus started: folder layout, consent record and a draft definition of "opens" ([corpus/](../../corpus/README.md))
- [ ] Benchmark on macOS and Linux reference hardware (needs the machines; the exact commands are in [reference-hardware.md](../reference-hardware.md#how-to-measure))

**Carried forward.** These were listed under M1 but belong to later milestones:

- Working drawing tools: M2. Working bone tools: M3.
- Browser build of the app itself: M5, with the web build. The engine crates already compile to WebAssembly on every release.
- Change tracking, so only changed parts of a frame are recalculated: M3, when Smart Bones and mesh deformation make evaluation expensive. Today evaluation is 0.01 ms for 40 bones and 0.1 ms for 400, and tessellation is the larger cost.

**First measurements.** Windows 10, Intel Core i5-6200U with HD Graphics 520 (a 2015 low-end integrated GPU, well below the "mid-range laptop" in the budget and proposed as the [floor machine](../reference-hardware.md#the-floor)), DirectX 12, release build:

| Scene | App (1280×800 window, no vsync) | CLI GPU render (1280×800, offscreen) | CPU per frame | Save | Load + validate |
|---|---|---|---|---|---|
| Benchmark, 40 bones, 81 shapes | **165 to 183 fps** | **123 fps** | 0.37 to 0.65 ms | 11.5 to 15.5 ms | 30.5 to 32.8 ms |
| Stress test, 400 bones, 801 shapes | 156 fps | 84 fps | 2.2 to 3.5 ms | 17.6 to 33.0 ms | 79.7 to 100 ms |

Ranges are from separate runs on different days. The CLI figure is lower than the app's because it waits for the GPU after every frame instead of overlapping CPU and GPU work. The 60 fps budget holds with plenty of room on this machine. The benchmark rig does not use Smart Bones or weighted deformation yet (they arrive in M3), so expect these numbers to fall as those features land; every release build runs the benchmark so regressions show up.

**Known driver issues.** The Vulkan driver for Intel HD Graphics 520 crashes the process while loading, before wgpu can report an error, and its OpenGL driver crashes in about 1 of 40 runs as the process exits, even when it was only loaded to list adapters. Fanimate therefore uses DirectX 12 on Windows and enables OpenGL only when DirectX 12 has no hardware adapter; `WGPU_BACKEND` (for example `vulkan` or `gl`) still overrides this.

Exit check: an artist can draw, animate by keyframes, save and recover after a forced crash.

- [x] Brush strokes stored as a centreline plus a width profile (`.fnm` version 1, [spec](../spec/fnm.md#width-profiles)): pen pressure and naturally tapered ends, simplified to few editable points and joined with smooth curves, so there are no odd curves at stroke ends (P9)
- [x] Stabiliser that smooths shaky lines without lagging: the line on screen always reaches the pen and ends where it lifts
- [x] Freehand tool that reads pressure from pens and touch screens through the windowing layer (not yet tried on tablet hardware), a live preview drawn by the real renderer, and a brush-size cursor; drawing with no vector layer selected makes a new layer, inside a selected group or bone layer
- [x] Rectangle and Ellipse tools (Shift for square or circle, Alt from the centre)
- [x] Eraser that cuts strokes and lines where it passes and removes shapes it covers; one drag is one undo step
- [x] Paint Bucket (fills shapes, recolours brush strokes) and Eyedropper
- [x] Select Points and Transform Points: click, Shift or Ctrl-click and box selection; drag to move with curve handles following; Delete, Select All and Select None act on points while a point tool is active
- [x] Style panel: line colour, width, outline, fill, smoothing, taper and eraser size for new artwork, remembered between sessions
- [x] Exact hit testing (inside fills, near strokes) for selection, Paint Bucket and Eyedropper
- [x] Crash recovery journal: after every action the open project is copied, in the background and one changed layer at a time, to a recovery folder; after a crash, the next start offers the unsaved work. A test kills a real process mid-session and checks the work comes back intact
- [x] Open Sample now asks about unsaved changes like New and Open (it used to discard them)
- [x] Add Point (Moho's: click a line to add a point on it without changing its shape, drag from an open end to extend, drop on the other end to close, drag in empty space to start a line) and a Pen (Illustrator's: click for corners, drag for smooth points, click the first point to close, Enter or Esc to finish)
- [x] Per-layer undo history that survives a crash, with a History panel: each step stores only the top-level layers it changed, sharing the rest with the step before; the history is journalled with the work (each layer state written once) and comes back with it after a crash; click any step to go to it; Undo on Selected Layer (Ctrl+Alt+Z) takes one layer back to before its own last change and leaves the rest alone. Up to 1000 steps are kept
- [x] Timeline key editing: drag keys to retime them (with the keys of the other selected layers on that frame; dropping on a key replaces it), choose interpolation (smooth, linear, step) from the key menu or the Animation menu; keys show their interpolation (round, diamond, square)
- [x] Boolean shape tools: Union, Subtract Front Shape and Intersect on the shapes with selected points (Edit › Combine Shapes, the Tools panel, the canvas menu). Curves come back as few smooth points; sharp corners stay sharp
- [x] Animating points (point keyframes, `.fnm` version 2, [spec](../spec/fnm.md#point-keyframes)): Add Keyframe on a vector layer keys its drawings too, and then moving points on another frame sets a point key there (the auto-key rule); drawings interpolate point by point. Erasing and combining leave animated shapes alone rather than lose their animation
- [ ] Usability pass with an artist, then the exit check

Not yet tested by hand: pen pressure on a real tablet, and the drawing tools' feel at different zooms. The editing logic behind every tool is covered by unit tests.

### M3: Rig (built; exit check outstanding)

Exit check: a character from a PSD is rigged and animated; 40-bone rig at 60 fps.

- [x] Bone tools: Add Bone (draws chains from the selected bone; makes a bone layer if none is selected), Select Bone (edits the rest pose by dragging joint or tip), Manipulate Bones (inverse kinematics by default, Alt for one bone, always keying the current frame so the rest pose is kept), Delete removes a bone and its children keep their place
- [x] Bone settings in Properties: name, length, angle limits, pinned (IK stops there) and strength
- [x] Binding: Bind to Selected Bone (Ctrl+B, rigid, keeps artwork in place on screen), Bind Smoothly (Ctrl+Shift+B, per-point weights from bone distance), Release from Bones, and Paint Weights (W) to brush weights for the selected bone
- [x] Smart Bones and the Actions panel: regular actions inserted into the timeline, Smart Bone actions that reshape artwork and turn other bones as their driver turns, several adding up; actions edited in place with a banner over the timeline ([spec](../spec/fnm.md#actions))
- [x] Mesh deformation: image layers bend with bones on a mesh (8×8 by default) with automatic weights
- [x] Image layers and PSD import: File › Import (Ctrl+I) brings in PNG and JPEG pictures, and Photoshop files as a group of image layers with their groups, positions, visibility and opacity; pictures live in the project's `media` folder, stored once, and render on the GPU like everything else
- [x] Rig health check in Properties: bones that move nothing or have no length, Smart Bones that do nothing yet, no longer fit their artwork, or clash with another on the same driver, and keyframes on hidden layers
- [x] The benchmark rig now has 10 Smart Bones, as the Gate 1 budget specifies
- [ ] Exit check with a tester and a real PSD character
- [ ] Benchmark on the reference hardware (macOS and Linux still outstanding from M1)

Not in M3, and why:

- **Rig templates, retargeting and physics** (WS5) are left for later: templates need artwork and testers, and the roadmap allows physics to slip first. They are not part of the M3 exit check.
- **Per-limb FK/IK blending**: posing uses IK interactively and stores ordinary keys, which is how Moho animators work; a stored IK target that blends with FK can follow if testers ask for it.
- **Weighted PSD rigs in other tools' formats** wait for the M5 importers.

- [x] Onion skin (Alt+O): earlier and later drawings or frames tinted in two colours, with how many, keys only or every frame, and selected or all layers, remembered between sessions

- [x] Switch layers: one child shown at a time, chosen by name on keys from the layer and key menus or Properties; the timeline names each key's choice ([spec](../spec/fnm.md#type-switch))

- [x] SVG import: each top-level group (Inkscape and Illustrator layers) becomes a vector layer; outlines, solid colours, opacity, line widths and transforms come through, even-odd fills are refitted, and the status says what was simplified or left out (text, pictures, gradients, clips, masks, filters)
- [x] Video export v1: File › Export Video (Ctrl+Shift+R) to MP4 or MKV (H.264 with the project's sound as AAC), animated GIF or PNG sequence, at any size and frame range. - [x] Video export v2: no bundled FFmpeg. Preferences › Video formats finds or chooses FFmpeg and says what it adds; the Export window groups formats and says what makes each. Every route converts and tags BT.709. `fanimate-cli formats` lists the routes
- [ ] Exit check with a tester
- [ ] Legal sign-off on the codec approach and the H.264 patent question ([review scope](../legal/review-scope.md), section 4)

- **Sound in AV1 export**: waits for a suitable Opus encoder in Rust. MP4 (H.264) carries sound.
- **Other sound formats** (MP3, OGG): WAV is what Rhubarb reads and what dialogue recording tools produce; others can follow.

## 1. Branding assets

### 1.1 Brand direction

**Purple is the brand colour.** It suits Fanimate for three reasons:

- It reads as creative and imaginative, and is not tied to the red of Adobe or the blue-greys of most developer tools.
- It sits well on dark backgrounds, which is where animators work for hours.
- It leaves room for warm accent colours (amber, coral) that mark animation state such as keyframes and the playhead.

**Personality:** friendly, capable, a little playful. It should feel like a tool made *by* animators, not an enterprise suite.

**Taglines to test:**

| Tagline | Tone |
|---|---|
| *Rig it. Draw it. Move it.* | Direct; names the three strengths |
| *Animation, unlocked.* | Reflects "nothing locked away" and the free, open model |
| *Free to animate.* | Short; works for the Nigeria and education audience |
| *Every frame yours.* | Reflects open file format and ownership of work |

Recommended starting pick: **"Free to animate."** It is short and states the main difference from Moho, Harmony and Animate.

### 1.3 Theme suggestions

Phase 1 ships **three built-in themes** plus an accessibility option. Themes are defined as design tokens (a single file of named values, such as `--panel`, `--accent`), so the UI never hard-codes a colour and the community can add themes later through the Phase 2 and 3 extension system.

| Theme | Character | Notes |
|---|---|---|
| **Fanimate Night** (default) | Deep purple-tinted dark. Violet-400 accent. | The default, because most animators work in dim rooms and dark panels stop the UI competing with artwork. |
| **Fanimate Day** | Light lavender-white. Violet-600 accent. | For bright studios and classrooms; also the theme of the website and docs. |
| **Fanimate Studio Grey** | Mid-dark neutral with a purple accent. | A grey UI for colour-critical work, where a tinted surround can bias how the artist judges colour. Offer this for the canvas surround at minimum. |

**Theme rules:**

- **The canvas surround is neutral by default.** Even in Night, the pasteboard around the artboard should be switchable to neutral grey, since coloured surrounds distort colour judgement.
- **Purple marks interaction, not content.** Selection outlines, focus rings, active tools and primary buttons are purple. Artwork, onion skins and bones use their own colours, so purple never gets confused with what the artist is drawing.
- **Keep Moho's layout, not its look.** The product vision says Fanimate follows Moho Pro's layout and workflow but draws its own icons and styling. A distinctly purple, rounded theme helps with that and with the legal position noted in the vision.
- **Corner radius and density:** 6 px panel corners, 4 px controls, with a *Compact* density option for laptop screens. Animation tools are dense, so compact must be a first-class setting.
- **Motion:** UI transitions at 120 to 160 ms, ease-out. An animation app should feel responsive. Respect the system "reduce motion" setting.

**Suggested typography** (all open licences, so they can ship in the app and repo):

| Use | Font | Why |
|---|---|---|
| UI | **Inter** | Clear at small sizes, wide language coverage, good on high-DPI screens |
| Numbers and code (timeline frame numbers, scripting console) | **JetBrains Mono** | Tabular digits so frame counts do not jitter |
| Wordmark | A geometric rounded sans such as **Nunito** or **Quicksand**, customised | Matches the friendly personality; customise the letters so the logo is not simply a font |

Check the licence on every font before bundling, and keep the licence texts in the repository.

### 1.4 Name and wordmark

- **Wordmark:** lowercase *fanimate* in a rounded geometric sans. Lowercase reads friendly and open-source; the tall *f* and *t* give shapes to play with.
- **Possible detail:** the crossbar of the *f* or the dot of the *i* is the one place to add character, such as a small bone joint or a keyframe diamond. Do only one; more becomes noisy.
- **Lockups:** icon only, icon plus wordmark horizontal, and wordmark only. Provide each in violet on light, white on violet, and white on dark.
- **Clear space:** the height of the *i* dot on every side.
- **Minimum size:** icon 16 px (for taskbars and file-type icons), wordmark 80 px wide.

**Name check before committing.** The vision already requires a legal review before 1.0. Do a trademark and domain search for "Fanimate" in M0, not M6, because every asset below is built on the name. Check the app-store, GitHub, crates.io and PyPI namespaces too.

### 1.5 App icon concepts

The icon must work at 16 px in a taskbar and at 1024 px on a splash screen, so it needs one bold shape, a limit of two or three colours, and no fine detail. Every concept below is purple and is drawn from scratch, with no resemblance to Moho's, Adobe's or Toon Boom's icons.

| # | Concept | Description | Strength | Weakness |
|---|---|---|---|---|
| **A** | **Bone-F** (recommended) | A rounded-square violet tile. A white letter *F* built from a thick stroke with a round joint node where the arm meets the stem, like a bone with a pivot. | Says *rig* and *Fanimate* at once. The joint circle survives at 16 px. | Needs care so it does not look like a generic "F" app icon. |
| **B** | **Onion-skin F** | A solid white *F* in front of two fainter, offset copies in lighter purples, suggesting onion skinning. | Says *frame-by-frame animation*. Visually distinctive. | The faint copies disappear at small sizes, so a 16 px version must drop to one copy. |
| **C** | **Bezier-F** | The *F* drawn as a single vector curve with two visible anchor points and handles. | Says *vector drawing* and appeals to illustrators. | Handles are fine detail; too technical for beginners. |
| **D** | **Keyframe diamond** | A white diamond (the universal keyframe marker) on violet, with a small trailing arc suggesting motion. | Extremely simple; scales to any size. | Generic. Many timeline tools use diamonds. |
| **E** | **Flipbook corner** | A violet page with the corner peeling up, an *F* on the visible page. | Friendly and nostalgic; speaks to education. | Detailed, and the peel does not read at 16 px. |

**Recommendation: Concept A (Bone-F), with Concept B as the splash-screen and marketing treatment.**

- A is the one app icon, in all sizes.
- B appears as a larger illustration on the splash screen and website hero, where the onion-skin layers have room to show.
- D's diamond is reused as a small brand motif: loading indicators, bullets in docs, the dot of the *i*.

**Construction brief for Concept A** (to hand to a designer):

- 1024 × 1024 canvas, rounded-square tile with a 22% corner radius, filled with a violet-500 to violet-700 diagonal gradient.
- *F* centred, made of a 12%-width stroke with round caps; the arm joins the stem at a circular node 1.5× the stroke width.
- A white F on violet-500 tile gives 4.7:1 contrast. Keep the tile at violet-600 or darker for the 16 and 32 px versions to widen that margin.
- Deliver a simplified 16 px and 32 px variant (thicker stroke, no gradient) rather than only scaling the large icon down.

## 3. Workstreams

Eight workstreams run in parallel. Each lists its main tasks, its dependencies and what "done" means.

### WS1. Core engine

| Task | Detail |
|---|---|
| Scene graph | Layers, groups, transforms, parent-child, switch layers |
| Animation curves | Keyframes, interpolation types (linear, step, smooth, bezier), channels |
| Bones and deformation | Bone hierarchy, FK, IK solver, weight-based mesh deformation |
| Undo and history | Per-object undo that survives a crash; journal of every action |
| Change tracking | Dirty-flag system so only changed bones, shapes and effects are recalculated (this underpins the 60 fps budget) |
| Headless mode | Engine builds without UI code so a command-line renderer can use it |

**Done when:** a scene can be built, animated, saved and re-opened from the command line, with no UI, and the results are deterministic.

### WS2. Renderer

| Task | Detail |
|---|---|
| wgpu setup | Vulkan, Metal, DirectX 12, WebGPU backends |
| Vector rendering | GPU tessellation of paths, fills, gradients, strokes with variable width |
| Compositing | Layer blending, masks, opacity, groups |
| Shared render path | The canvas and the final export use the same renderer, so output matches the screen |
| Large-scene performance | Culling, caching of static layers, instancing |

**Done when:** the benchmark scene (see section 5) holds 60 fps on the reference mid-range laptop, on all three desktop platforms.

### WS3. File format and data safety (`.fnm`)

| Task | Detail |
|---|---|
| Specification | Published spec for the folder and zipped forms; version number from day one |
| Serialisation | Human-readable text per layer or rig, binary assets alongside |
| Validator | Broken references, duplicate and out-of-range keyframes, orphaned data |
| Self-repair | Fix what is safe automatically, report what is not |
| Autosave journal | Every 60 seconds plus every action, recover to the last action after a crash |
| Migration | Format versioning so old files always open |

**Done when:** a fuzz and corruption test suite cannot produce an unopenable file, and a forced crash loses no more than the last action.

### WS4. Drawing and frame-by-frame

| Task | Detail |
|---|---|
| Vector brush | Centreline plus width profile; pressure, tilt and speed input; natural tapered ends |
| Stabiliser | Adjustable smoothing with prediction |
| Shape and point tools | Pen, add and transform points, booleans, primitives |
| Clean-up | Auto-close gaps, merge strokes, pencil-to-ink |
| Frame-by-frame layers | Drawing on any frame, exposure, hold and repeat |
| X-sheet and timeline | Two views of the same data |
| Onion skin and light table | Colour-coded range, key-drawings-only filter, flipping |
| Sub-layers | Rough, line, colour and overlay inside one drawing |
| Pen tablet support | Wintab and Windows Ink, macOS tablet events, Linux libinput |

**Done when:** a short hand-drawn walk cycle can be created entirely in Fanimate, and a test artist reports no "locked to frame 0" or end-of-stroke curve artefacts.

### WS5. Rigging and lip sync

| Task | Detail |
|---|---|
| Bones | Creation, editing, constraints, FK and IK with per-limb blend |
| Smart Bones | Driver bones, multiple inputs, response curves, on-canvas controls |
| Mesh deformation | Auto weights, weight painting |
| Templates | Biped, quadruped, bird, face starter rigs |
| Retargeting | Move animation between rigs of different proportions |
| Rig health check | Unused bones, conflicting drivers, hidden-channel keys |
| Physics | Bone springs and gravity, bake to keyframes (stretch goal if time is short) |
| Rhubarb integration | Bundle the tool, map mouth shapes to a switch layer or Smart Bone, editable lip-sync track with waveform |

**Done when:** the benchmark rig (40 bones, 10 Smart Bones) plays at 60 fps, and a new tester rigs a character from a PSD in under 30 minutes (the success metric from the vision).

### WS6. Import and export

| Task | Detail |
|---|---|
| SVG importer | Full SVG 1.1 and SVG 2 drawing content; structure, names and styles preserved; import report |
| PSD importer | Layers, groups, blend modes, clipping, names |
| Moho importer | Layers, vector shapes, bones, Smart Bone actions, switch layers, keyframes, audio, camera |
| Animate importer | Symbols, timelines, drawings, classic and shape tweens, audio |
| Video export | MP4 (H.264), WebM, GIF, PNG sequence, with audio |
| Import test corpus | Collect a library of real-world test files (see section 5) |

**Done when:** at least 90% of the Moho test corpus opens (a Gate 1 criterion), and every import writes a report listing anything that did not map.

**Legal rule:** write importers from public documentation and the file contents only, never from the original programs' code or decompiled binaries. Log every source consulted.

### WS7. Interface

| Task | Detail |
|---|---|
| UI shell | GPU-drawn docking system, tabbed and floating panels, saved workspaces |
| Default layout | Tools left, canvas centre, Layers, Style and Actions right, timeline bottom |
| Themes | Token-based theming (Night, Day, Studio Grey) from section 1 |
| HiDPI | Correct at 100% to 300% scaling, per-monitor |
| Command palette | Search every command and setting |
| Keymaps | Two presets: Fanimate (standard editing shortcuts, the default) and Moho; chosen on first launch, switchable any time. Full remapping and Harmony-style keys can follow in Phase 2 |
| Title-bar menus | Menus share the window title bar; custom caption buttons and resizing on Windows and Linux, native controls on macOS |
| Right-click menus | Context menus on every panel, reusing the main menu commands and showing their shortcuts (P23) |
| Properties panel | Layer and project settings edited live in a docked panel, never in modal dialogs (P23) |
| Accessibility | Keyboard navigation, screen-reader labels where the platform allows, scalable fonts |
| First-run experience | Short interactive tutorial, "Coming from Moho / Animate" guide |

**Done when:** a Moho user, given no instructions, finds the bone tool, makes a bone and keys a pose in under five minutes in a usability session.

### WS8. Platform, release and community

| Task | Detail |
|---|---|
| Build and CI | Automated builds and tests on Windows, macOS, Linux and WASM for every change |
| Installers | Windows installer, macOS DMG (signed and notarised), Linux AppImage, Flatpak and distro packages |
| Self-updater | Checks GitHub releases in the background, downloads a new version, verifies its signature and installs it when the user agrees, rolling back if anything fails (P21). Works offline without complaint, can be turned off, can pin a version for a production, and never replaces the app while the render queue is rendering. Flatpak and distro packages update through their own package managers |
| Web build | WebGPU build with documented limits; project sync with desktop |
| Telemetry (opt-in) | Crash reports and anonymous performance data, off by default, to measure the crash-free metric |
| Public repo | Licence files, contributing guide, code of conduct, issue templates |
| Public roadmap | Roadmap and voting in the issue tracker |
| Release trains | Monthly stability releases and four-monthly feature releases from the first public build |
| Docs | User manual skeleton, `.fnm` specification, architecture overview |

**Done when:** a stranger can download, install, open the sample project, update to the next release, and file a bug, on any of the three desktop platforms, without help from the team.

### 4.1 Schedule

The first plan gave M0 to M2 the first five months and the whole phase about 12 months. With AI-assisted coding, M0 to M5 were built in about a week, and everything still open in them waits on people, hardware or accounts, not code. Writing code no longer sets the schedule. These do:

| Constraint | Why it takes calendar time | Gates |
|---|---|---|
| Human review | Every change is reviewed by a person (section 6). The M2 changes alone were about 9,000 lines | Every milestone |
| Artists and Moho animators | The exit checks for M2 to M4, the WS7 usability session and the Gate 1 usability test need real users. No advisers are recruited yet | M2, M3, M4, M6, Gate 1 |
| Reference hardware | The 60 fps budget is measured on specific machines the team needs access to | M1, M3, M6, Gate 1 |
| Import test corpus | 100 Moho and 50 Animate files, each with recorded consent. None are collected yet, and the importers cannot be measured without them | M5, Gate 1 |
| Legal review | External. The [video export note](../legal/video-export.md) asks counsel to settle the codec question before 1.0; since 0.2.0 MP4 uses the system's encoder and Fanimate ships no H.264 encoder. Templates add forms for licences and consent ([release-1.0.md](release-1.0.md#56-provenance-licences-and-consent)) | Gate 1 (end of Phase 2) |
| Code signing | Apple Developer account and a Windows code-signing certificate; identity checks take days to weeks. Needed for the public launch; until then the installers show the systems' unknown-publisher warnings | Gate 1 (open the accounts early) |
| Public beta | 99.5% crash-free sessions means fewer than 1 crash in 200 sessions, which takes thousands of opt-in sessions to show. Users, crash reports and stability releases need weeks, not days. **Now runs once, at the end of Phase 2 (M15b)**; the closed alpha gives early numbers only | Gate 1 (end of Phase 2) |
| Films, examples and handmade templates | Made by people, in builds that have the Phase 2 features; see [release-1.0.md](release-1.0.md) | Gate 1 (end of Phase 2) |

**Build estimates.** The M5 build took about two days. The importers are the part most likely to need more work: they are tuned against real files, and only a handful of openly licensed files were available to build them; the corpus will show what is missing. The M2 to M5 exit checks run alongside the closed alpha, and anything they find is fixed before new features.

**Start now, because they are on the critical path:**

1. Recruit the advisers (first 30 days, item 10). The M2 to M5 exit checks all need testers, and Moho animators need to judge what the importer produces.
2. Collect the import corpus. At least 100 Moho files with consent are needed before the importers can be measured.
3. Finish the codec part of the legal review (section 4 of the [review scope](../legal/review-scope.md)) before 1.0.
4. Get the macOS and Linux reference machines, or access to them.
5. Open the Apple Developer and Windows code-signing accounts. Identity checks can take weeks; they are needed by the public launch at the end of Phase 2, and until then the installers show the systems' unknown-publisher warnings (the updater's own signature check does not depend on them).

The rest of Phase 1 (the close-out) runs alongside Phase 2: the corpus, the exit checks with testers and the other platforms' benchmarks. These take calendar time however fast the code is written. The public beta, which this plan used to put here, now runs once at the end of Phase 2. Re-plan when the closed alpha has the importer pass rate and the first crash numbers from testers.

**Rules for the schedule:**

- **Building ahead is fine; closing early is not.** Work on a milestone can start while the previous one waits on an exit check, but a milestone closes only when its exit check passes, and fixing what an exit check finds comes before new features.
- **No milestone closes with known data-loss bugs.** Data safety (P13, P14) is a standing requirement, not an M6 task.
- **A closed alpha until Gate 1, not a public one.** Alpha builds go to testers and animators through the normal release process, with no announcement or launch activity (changed on 2026-10-30; this rule used to say "a public alpha at M5, not at M6"). The public beta that produces the crash-free measurement runs once, at the end of Phase 2.
- **Moho and Animate importers wait until M5 on purpose.** They depend on a stable scene model. Starting them at M1 would mean rewriting them whenever the model changes. Start collecting the test corpus in M1, though, since that costs nothing.
- **If a milestone slips, cut scope, not quality.** The first things to cut are physics (WS5) and the Animate `.fla` importer's shape tweens, in that order.

## 5. Gate 1 acceptance tests

Gate 1 is the release decision for version 1.0. It is not a date. **Since 2026-10-30 it is decided at the end of Phase 2, not Phase 1**, and it also includes the old Gate 2, the showcase and the handmade templates: the full list is in [release-1.0.md, section 6](release-1.0.md#6-gate-1-criteria-now), and the tests the Phase 2 features add are in [phase-2.md, section 6](phase-2.md#6-gate-1-at-the-end-of-phase-2). The criteria and tests below are unchanged and are measured as the work goes on, so the numbers in section 5.3 keep being updated.

### 5.1 Criteria from the vision

| Criterion | How it is measured | Target |
|---|---|---|
| Performance budget | Benchmark scene on the reference mid-range laptop | **60 fps** with a 40-bone character and 10 Smart Bones |
| Project open time | A 5-minute episode scene, cold start | **Under 3 seconds** |
| UI responsiveness | Automated UI action timing across the main workflows | **No single action over 100 ms** |
| Stability | Opt-in crash telemetry across the beta | **99.5% crash-free sessions** |
| Moho compatibility | The Moho test corpus (below) | **90% of files open** |

### 5.2 Supporting tests added for Phase 1

| Test | Pass condition |
|---|---|
| Crash recovery | A forced kill at a random moment recovers to the last action in 100 of 100 trials |
| File corruption | Fuzzing the `.fnm` format never produces a crash; the validator repairs or reports every case |
| Cross-platform parity | The same scene renders pixel-identical, within a small tolerance, on Windows, macOS and Linux |
| Canvas versus export | Exported frames match the on-screen canvas for the benchmark scene |
| SVG conformance | A defined set of SVG test files imports with matching geometry, plus an import report for unsupported features |
| Fresh install | Installers run on clean Windows 10/11, macOS 13+ and Ubuntu, Fedora and Flatpak, and open a sample project |
| Self-update | An installed build updates to the next release on Windows, macOS and the AppImage; a corrupted or unsigned download is rejected and the installed version keeps working; with no network the app starts and works normally |
| Accessibility | High-contrast theme and keyboard navigation work through the main workflows; contrast tests in section 1.2 pass |
| Usability | A first-time Moho user and a first-time non-Moho user each complete the "rig a character" task; median under 30 minutes |
| Licence audit | Every dependency and bundled font, library and model has a compatible licence recorded |
| Legal review | Interface, naming and importers reviewed (required before 1.0 in the vision) |

### 5.4 The test corpus

The 90% Moho compatibility target needs real files, so start collecting in M1.

- **Moho:** 100 or more files, from simple to complex, including known tricky cases such as the negative-keyframe bug (P13), nested switch layers and heavy Smart Bone rigs. Source them from willing community members and from permissively licensed samples.
- **Animate:** 50 or more `.fla` and `.xfl` files with symbols and tweens.
- **SVG:** the public SVG test suites plus real exports from Illustrator, Inkscape, Affinity and Figma.
- **PSD:** layered character sheets with groups, blend modes and clipping masks.
- **Consent and licensing:** record the permission for every contributed file. Never put private studio files in the public repository.

Define "opens" precisely before testing: the file loads without error, the layers, bones and timing are present, and a short render matches a reference render within an agreed tolerance. Without this definition the 90% figure is easy to hit and means little.

## 6. Phase 1 risks

These are in addition to the project-wide risks in the vision.

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Rust and wgpu GPU differences cause rendering bugs on some drivers | High | Medium | Test matrix with real hardware early (M1); software-rendering fallback |
| Vector tessellation on the GPU is slow or looks wrong for thick or overlapping strokes | Medium | High | Prototype stroke rendering in M1; keep the width-profile model independent of the renderer so techniques can be swapped |
| Moho and Animate importers eat unbounded time on edge cases | High | High | Define "opens" tightly; ship an import report; accept the 90% target rather than 100%; cut tweens first |
| Smart Bone behaviour does not match Moho users' expectations | Medium | High | Test against the Moho corpus rigs as soon as M3 begins; involve Moho animators in design reviews |
| Scope pressure from the whole feature list | High | High | Section 2.2 out-of-scope list is binding; any addition needs a removal |
| WebGPU limits make the browser build too weak | Medium | Low | Position as learning and review, as the vision says; ship with documented limits |
| Early contributors and the community are too few | Medium | Medium | Public repo from M0; "good first issue" labels; publish architecture docs early |
| Code quality problems, especially if AI-assisted coding is used | Medium | High | Human review on every change; benchmarks and tests in CI from M1 |
| Name or trade-dress challenge | Low | High | Trademark search in M0 (done); original icons and styling; legal review before the 1.0 launch (end of Phase 2) |
| Codec and font licence issues | Medium | Medium | Restrict Phase 1 export to the codecs listed in section 2.2; audit fonts and libraries |

## 7. First 30 days

A concrete starting list, in priority order.

1. **Trademark and domain check** for "Fanimate"; reserve the domain, GitHub organisation, crates.io and PyPI names.
2. **Choose the brand direction:** confirm purple, pick one icon concept from section 1.5 and one tagline.
3. **Commission or draw the logo and Concept A icon**; produce the 16 to 1024 px set.
4. **Write the design-token file** (colours, radii, spacing, type) from section 1.2 and 1.3. This is the first file in the UI codebase.
5. **Create the public repository:** dual MIT / Apache 2.0 licence files, README with the banner, contributing guide, code of conduct, issue templates.
6. **Set up CI** that builds a "hello window" on Windows, macOS, Linux and WASM.
7. **Pick the reference hardware** for the performance budget and write down its exact specification, so "mid-range laptop" is a defined machine.
8. **Build the two benchmark scenes** (40-bone character, 5-minute episode) as the first test assets, even if only as drawings of the plan.
9. **Start the import test corpus** and the consent record for contributors.
10. **Recruit three to five advisers**: two Moho animators, one Animate user, one studio technical director. They seed the steering group and the usability tests.
